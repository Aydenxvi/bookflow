### Phase 4 automation — notifications, worker, status history, analytics — verified against real PostgreSQL and a real headless browser

**Notification enqueueing** (`apps/api/app/services/notifications.py`, new file, hooked into the existing `app/services/booking.py` rather than into routers, so customer- and admin-created bookings are both notified identically):

**`apps/worker`** — a new package, built from scratch, picked up jobs with `SELECT ... FOR UPDATE SKIP LOCKED`:
- Deliberately **fully self-contained** — does not import anything from `apps/api` (both packages have a top-level `app` module, which would collide, but more importantly a worker and an API shouldn't share a live ORM mapping across a process boundary). Declares its own hand-written SQLAlchemy **Core** `Table` objects in `app/tables.py` as a documented, intentionally-hand-kept mirror of the relevant columns of `apps/api`'s real schema — a maintenance cost flagged explicitly in both `apps/worker/README.md` and NEXT_STEPS.md, not hidden.
- Claims one job per transaction, holds the row lock for the full duration of the Telegram API call rather than introducing an undocumented intermediate "processing" status — documented in `app/claim.py`'s docstring as a deliberate simplicity/safety trade-off: a crash mid-send just leaves the job `PENDING` for the next poll, instead of a job stuck invisibly in a half-processed state.
- Exponential backoff (`backoff_base_seconds * 2**attempts`, capped at `backoff_max_seconds`), terminal `FAILED` status at `max_attempts`.
- `BUSINESS_DAILY_SUMMARY` jobs are scheduled with **no persistent scheduler state**: each poll computes "the next business-local `daily_summary_local_hour`:00" via `zoneinfo`, uses that date in the job's `dedupe_key`, and relies purely on dedupe-key-existence to avoid duplicates and to naturally roll over to the next day once today's has been sent.
- Talks to Telegram via a direct `httpx` POST to the raw Bot API (`sendMessage`), not `aiogram` (which `apps/bot` uses for a different purpose — launching the Mini App) — kept thin on purpose.
- **25 new pytest tests**, all passing against a dedicated real PostgreSQL database (`bookflow_worker_test`, not SQLite/mocks — created via `createdb` specifically because `SELECT ... FOR UPDATE SKIP LOCKED` and this schema only exist in real Postgres): message rendering for every job type, claim/skip-locked/backoff/terminal-failure behavior, daily-summary date-bucketing and dedupe across multiple poll cycles including a real DST-adjacent business timezone, and a full integration pass (seed a job → run one worker cycle → confirm it was sent and marked `SENT`, with a mocked Telegram HTTP client — never the real API).
- **A genuine cross-service smoke test** (`scratchpad/smoke_e2e.py`, not part of the repo): created a real business/owner/customer/Telegram-identity/booking through `apps/api`'s actual service layer against the real `bookflow` database, confirming the worker's hand-kept `tables.py` mirror actually matches what `apps/api`'s real Alembic-migrated schema produces — not just the worker's own self-created test schema, which would have missed any drift between the two.

## Environment constraints for this session
- **No Docker daemon** is available in this sandbox (the `docker` CLI exists but there's no running daemon) — PostgreSQL was installed and run directly instead (`postgresql-16` package, started via `service postgresql start`), and the frontend was run with `npm run dev` / built with `vite build` directly rather than through its Dockerfile. `docker-compose.yml` (api + web + worker + an opt-in `bot` profile) and all four Dockerfiles are written but have not themselves been exercised in this session — worth a real `docker compose up` pass on a machine/CI that has Docker.
- No Telegram bot token available — `TELEGRAM_BOT_TOKEN`/`BOT_TOKEN` is unset; the Telegram auth *code path* on the backend is fully implemented and unit-tested against a fake signed token, the bot's handler code imports and registers correctly, and the worker's `httpx` call to the raw Bot API is implemented and tested against a mocked HTTP client — but none of the three has been exercised against the real Telegram API or a live bot/client.
- `apps/worker` was run directly (`python -m app.main`) against a separate `bookflow_worker_test` database for its own test suite, and against the real `bookflow` dev database for the cross-service smoke test — not through Docker, for the same reason as the rest of this session.
- **This sandbox's own egress allowlist** (separate from "no Docker") blocks two hosts the frontend references: `ui.shadcn.com` (the shadcn CLI's registry — worked around by hand-writing the UI primitives, see above) and, at runtime in the Playwright test browser only, `fonts.googleapis.com` and `telegram.org` (the Google Fonts stylesheet and the official Telegram WebApp script tag). Both are ordinary public hosts that any real user's browser reaches fine — this only affected what the sandbox's own test browser could fetch, not the application code.
- No deployment target — deployment docs will describe steps, not a verified run.
