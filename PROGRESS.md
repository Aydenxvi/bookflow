# PROGRESS.md — Current Implementation Status

Last updated: 2026-11-01 (session 1, Phase 3 admin backend checkpoint)

## What exists right now

### Backend (`apps/api`) — functional, tested against real PostgreSQL
- FastAPI app (`app/main.py`) with CORS, structured logging, `/health`.
- 16 SQLAlchemy 2.x async models covering every entity in the spec (plus `AuditLog`), registered and migrated.
- Alembic migration `0001_initial_schema` — autogenerated from the models, plus a hand-written `btree_gist` EXCLUDE constraint (`excl_bookings_staff_overlap`) on a generated `tstzrange` column, scoped to active booking statuses.
- Availability engine (`app/services/availability.py`): real slot computation from business/staff hours, breaks, exceptions, existing bookings + buffer, lead time, advance window, business timezone — DST-safe (verified against a real spring-forward transition, see Validation below).
- Booking service (`app/services/booking.py`): create/cancel/reschedule/status-transition, with a Postgres advisory-lock + `SELECT ... FOR UPDATE` re-check in front of the DB exclusion constraint, idempotency keys, policy windows (lead time, advance window, cancellation/reschedule windows).
- Telegram `initData` verification (`app/core/telegram_auth.py`) implementing the documented HMAC-SHA256 algorithm exactly; demo-mode auth path (`app/routers/auth.py`) issuing a demo-scoped JWT.
- JWT session layer (`app/core/security.py`) + role/business-scoped authorization dependencies (`app/core/authz.py`).
- Routers: `auth`, `businesses` (profile/services/staff), `availability`, `bookings` (create/mine/cancel/reschedule).
- Seed script (`app/seed.py`): ATELIER — Modern Grooming Studio, 3 staff, 6 services, weekly schedules + breaks, one schedule exception, 2 historical bookings.
- Simple in-process rate limiter on booking creation (documented single-process limitation).

### Frontend (`apps/web`) — functional, driven end-to-end against the real backend

- UI primitives (`src/components/ui/`) hand-written in the shadcn/ui pattern (Radix UI primitives + `class-variance-authority` + `cn()`), **not** generated by the `shadcn` CLI — its registry host (`ui.shadcn.com`) is blocked by this sandbox's egress allowlist (confirmed: `403` at the proxy level, not a transient failure). Functionally and stylistically equivalent; documented in `apps/web/README.md` so a future session doesn't waste time re-attempting the CLI here.
- Telegram WebApp SDK integration (`src/lib/telegram.ts`) + automatic browser-demo-mode fallback (`src/lib/auth.tsx`): real Telegram `initData` is used when present and non-empty, otherwise `/api/v1/auth/demo` is called automatically, scoped to the seeded ATELIER business.
- Typed API client (`src/lib/api-client.ts`, `src/lib/api-types.ts`) and TanStack Query hooks (`src/lib/queries.ts`) covering every backend endpoint.
- Full booking flow: `HomePage` (business profile + services) → `SpecialistPage` (named staff or "any available") → `DateTimePage` (real slots from the availability engine, day chips + time grid, business-timezone-correct) → `ConfirmPage` (summary + optional notes, idempotency-keyed submit, 409-conflict handling) → `SuccessPage`.
- `AppointmentsPage` ("My Appointments"): upcoming/completed/cancelled tabs, cancel (confirm dialog, optional reason), reschedule (in-place dialog re-querying availability for the same service/staff and submitting a new time).
- `apps/web/Dockerfile` (multi-stage Vite build → nginx with SPA fallback) and `docker-compose.yml` `web` service — written, not run (see Environment constraints).

### Admin backend (`apps/api`, Phase 3) — functional, tested; no UI yet
- `app/schemas/admin.py`: all admin-facing Pydantic schemas — business profile update (with an IANA-timezone `field_validator`), `MeOut`/`MembershipOut`, service create/update/out, staff create/update/services-update/out, weekly-schedule + break + exception in/out, booking-policy out/update, manual-booking-create, booking-status-update, admin booking/customer out, dashboard summary/service-count/staff-count out.
- `app/routers/auth.py` extended: `POST /auth/demo-admin` (demo sign-in for the admin dashboard — issues a fresh synthetic user with a `BUSINESS_OWNER` membership on the demo business, isolated per call just like the existing `/auth/demo`) and `GET /auth/me` (who am I + which businesses can I administer, with what role — the admin frontend's first call after login).
- `app/routers/admin_services.py`: list (incl. archived)/create/update/archive/unarchive. Services are never hard-deleted — archiving flips `is_active`, since historical bookings snapshot their own price/duration independently.
- `app/routers/admin_staff.py`: list/create/update, service-assignment (replace-all), weekly working-schedule get/replace (shared helpers `load_schedule_out`/`replace_schedule`, reused by the business-hours endpoints below with `staff_id=None`), schedule-exception (leave/holiday/closure) list/create/delete.
- `app/routers/admin_business.py`: business profile get/patch (owner-only patch), operating hours get/put (reuses the staff-schedule machinery), booking policy get/patch (auto-creates a default policy row on first read).
- `app/routers/admin_bookings.py`: appointment calendar (date-range + staff/service/status filters, 92-day cap, ±14h UTC pad to safely bucket business-local days without resolving the exact timezone server-side), manual/walk-in booking creation (creates a lightweight guest `User`, goes through the same concurrency-safe `booking_service.create_booking` as the customer flow), booking status changes (routes `CANCELLED` through `cancel_booking` with a staff-override flag). Staff-role users are restricted server-side to their own bookings only — verified, not just documented (see tests below).
- `app/routers/admin_dashboard.py`: today/upcoming/completed/cancelled counts, a revenue estimate from completed bookings, top-5 popular services, top-10 staff workload — all via SQL aggregates, not Python-side counting.
- Every mutating admin endpoint writes an `AuditLog` row (`SERVICE_CREATED/UPDATED/ARCHIVED`, `STAFF_CREATED/UPDATED`, `SCHEDULE_UPDATED`, `SETTINGS_UPDATED`, `BOOKING_CREATED_MANUALLY`, `BOOKING_STATUS_CHANGED`).
- Role enforcement throughout: owner/manager can manage everything; staff can only view/act on their own bookings (never trusted from a query param — resolved server-side via `Staff.user_id`); everything is additionally scoped to the `business_id` in the URL via `RequireBusinessRole`, so a valid membership on business A is never honored for business B.
- **No admin frontend UI exists yet** — these endpoints are only reachable via direct HTTP calls (curl/Postman) or the automated tests below.

- **One real bug found and fixed**: `admin_staff.py::set_staff_services` looked up the `Staff` row (with its `staff_services` relationship eagerly loaded) *before* replacing the links, then looked it up again *after* committing the replacement, expecting the second lookup to return the fresh data. Because both lookups happened in the same `AsyncSession` and the `Staff` object was already in the session's identity map with `staff_services` already loaded, SQLAlchemy's `selectinload` silently skipped reloading it on the second query — the endpoint returned the **stale, pre-change** `service_ids` list in its response, immediately after a successful `200 OK`. A `pytest` test (`test_set_staff_services_replaces_links`) caught this directly (asserted the new `service_ids`, got the old/empty ones back). Fixed with an explicit `db.refresh(staff, attribute_names=["staff_services"])` right after the commit; re-ran the test to confirm. Note this only affected the HTTP response of that one call, not what ended up correctly stored in the database — a follow-up `GET` would already have shown the right data even before the fix — but it's exactly the kind of "the write looked like it worked but told you the wrong thing" bug that erodes trust in an admin UI fast.

- This pass **found and fixed a real, previously-unverified backend bug**: `apps/api/app/seed.py` used `db.delete(business)`, and because `Business.bookings` / `working_schedules` / `schedule_exceptions` lack an ORM-level cascade (unlike `staff`/`services`, which do), SQLAlchemy tried to null out their `NOT NULL` foreign keys in Python on the *second* reseed, raising `IntegrityError`. Every one of those FKs is already `ondelete="CASCADE"` at the database level, so the fix was to issue a raw SQL `DELETE` instead of an ORM `db.delete()`, letting Postgres cascade it correctly — verified by reseeding twice in a row successfully, with `pytest` (27/27) re-run clean afterward.

## Environment constraints for this session
- **No Docker daemon** is available in this sandbox (the `docker` CLI exists but there's no running daemon) — PostgreSQL was installed and run directly instead (`postgresql-16` package, started via `service postgresql start`), and the frontend was run with `npm run dev` / built with `vite build` directly rather than through its Dockerfile. `docker-compose.yml` (api + web + an opt-in `bot` profile) and all three Dockerfiles are written but have not themselves been exercised in this session — worth a real `docker compose up` pass on a machine/CI that has Docker.
- No Telegram bot token available — `TELEGRAM_BOT_TOKEN`/`BOT_TOKEN` is unset; the Telegram auth *code path* on the backend is fully implemented and unit-tested against a fake signed token, and the bot's handler code imports and registers correctly, but neither has been exercised against the real Telegram API or a live bot/client.
- **This sandbox's own egress allowlist** (separate from "no Docker") blocks two hosts the frontend references: `ui.shadcn.com` (the shadcn CLI's registry — worked around by hand-writing the UI primitives, see above) and, at runtime in the Playwright test browser only, `fonts.googleapis.com` and `telegram.org` (the Google Fonts stylesheet and the official Telegram WebApp script tag). Both are ordinary public hosts that any real user's browser reaches fine — this only affected what the sandbox's own test browser could fetch, not the application code.
- No deployment target — deployment docs will describe steps, not a verified run.
