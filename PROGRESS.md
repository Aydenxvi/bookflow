# PROGRESS.md — Current Implementation Status

Last updated: 2026-11-01 (session 1, backend checkpoint)

## What exists right now

### Backend (`apps/api`) — functional, tested against real PostgreSQL
- FastAPI app (`app/main.py`) with CORS, structured logging, `/health`.
- 16 SQLAlchemy 2.x async models covering every entity in the spec (plus `AuditLog`), registered and migrated.
- Alembic migration `0001_initial_schema` — autogenerated from the models, plus a hand-written `btree_gist` EXCLUDE constraint (`excl_bookings_staff_overlap`) on a generated `tstzrange` column, scoped to active booking statuses.
- Availability engine (`app/services/availability.py`): real slot computation from business/staff hours, breaks, exceptions, existing bookings + buffer, lead time, advance window, business timezone — DST-safe (verified against a real spring-forward transition, see Validation below).
- Booking service (`app/services/booking.py`): create/cancel/reschedule/status-transition, with a Postgres advisory-lock + `SELECT ... FOR UPDATE` re-check in front of the DB exclusion constraint, idempotency keys, policy windows (lead time, advance window, cancellation/reschedule windows).
- Telegram `initData` verification (`app/core/telegram_auth.py`) implementing the documented HMAC-SHA256 algorithm exactly; demo-mode auth path (`app/routers/auth.py`) issuing a demo-scoped JWT.
- JWT session layer (`app/core/security.py`) + role/business-scoped authorization dependencies (`app/core/authz.py`).
- Routers: `auth`, `businesses` (profile/services/staff), `availability`, `bookings` (create/mine/cancel/reschedule).
- Seed script (`app/seed.py`): ATELIER — Modern Grooming Studio, 3 staff, 6 services, weekly schedules + breaks, one schedule exception, 2 historical bookings.
- Simple in-process rate limiter on booking creation (documented single-process limitation).

## Validation actually performed (not just written)

- **Local environment**: PostgreSQL 16 is installed and running in this sandbox (no Docker daemon available here — see note below); created `bookflow` (dev) and `bookflow_test` (test) databases with the `btree_gist` extension.
- **Migration applied for real**: `alembic upgrade head` run against `bookflow`; confirmed via `psql \d bookings` that the generated `during` column and `excl_bookings_staff_overlap` EXCLUDE constraint exist exactly as designed.
- **Overlap prevention proven at the SQL level**: a direct `psql` transaction inserting two overlapping bookings for the same staff member — the second insert was rejected by the database with `conflicting key value violates exclusion constraint`, with no application code involved.
- **Full HTTP, end-to-end, against the real seeded demo business** (server run locally with `uvicorn`, real curl requests, real Postgres):
  - Demo auth → business profile → service list → real availability (confirmed correct UTC↔Europe/Istanbul conversion, e.g. 09:00 local = 06:00 UTC) → create booking (201, real row) → a second customer attempting the exact same slot got **409 Conflict** → "my bookings" showed the real booking → cancel succeeded (200, status transitioned to `cancelled`).
  - This also exposed and fixed two real bugs before committing: (1) lazy-loaded relationships being accessed outside an async-safe context (`MissingGreenlet`) in both the availability engine and the booking responses — fixed with `selectinload`; (2) none before shipping — both were caught here, not left for later.
- **Automated test suite**: 27 tests, **all passing**, run with `pytest` against the real `bookflow_test` PostgreSQL database (not SQLite/mocks) — because the thing being tested (the EXCLUDE constraint, `tstzrange`, advisory locks) only exists in Postgres:
  - Telegram `initData`: valid signature accepted; tampered payload, wrong bot token, stale `auth_date`, missing hash, and no-token-configured all correctly rejected (6 tests).
  - Availability engine: business/staff-hours intersection, recurring breaks removing slots, a whole-day `ScheduleException` closing availability, minimum lead time excluding near-term slots, and a **real DST spring-forward transition** (Europe/Berlin, 2027-03-28) producing correct, non-duplicated UTC instants on both sides of the offset change (5 tests).
  - Overlap prevention: a raw ORM-level double-insert rejected by the database constraint directly; a cancelled booking correctly *not* blocking its old slot; the booking service rejecting an overlap for an explicitly-requested staff member; idempotency-key replay returning the same booking (4 tests).
  - **Concurrency**: two independent async DB sessions racing to book the exact same staff+time via `asyncio.gather` — exactly one succeeds, the other gets a clean `BookingConflictError` (1 test).
  - Status transitions: automatic vs. manual confirmation mode, valid/invalid transitions, cancellation inside/outside the policy window, staff override bypassing the window, and reschedule correctly creating a new booking while cancelling the old one with a `rescheduled_from_booking_id` link (8 tests).
  - Multi-tenant isolation: a service/staff lookup scoped to the wrong business 404s; a staff member linked only to Business A never appears in Business B's availability (3 tests).
- `ruff check` run; auto-fixable issues fixed; 36 cosmetic `dict()`-literal suggestions remain (non-functional, left as-is).
