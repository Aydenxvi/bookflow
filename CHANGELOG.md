## 2026-11-02 — Phase 4 automation: notifications, worker, status history, analytics

- **Notification enqueueing** (`apps/api/app/services/notifications.py`, new): hooked into the existing `app/services/booking.py`'s create/transition/cancel/reschedule functions rather than into routers, so customer- and admin-created bookings both notify identically with no special-casing. Customer-facing jobs (`BOOKING_RECEIVED`/`BOOKING_CONFIRMED`/`BOOKING_CANCELLED`/`BOOKING_RESCHEDULED`) and business-facing jobs (`BUSINESS_NEW_BOOKING`/`BUSINESS_CANCELLATION`/`BUSINESS_RESCHEDULE`, respecting each business's own notification-preference flags) are resolved from real `TelegramIdentity`/`BusinessMembership` rows, not assumed. A reschedule sends exactly **one** combined notification, not a cancel-then-create pair — a new `suppress_notifications: bool = False` keyword-only parameter was added to `create_booking`/`transition_status` specifically to suppress the intermediate notifications that would otherwise fire during the internal cancel+recreate that a reschedule does under the hood. Reminder jobs are scheduled per `BookingPolicy.reminder_offsets_minutes` (already defaulted to 24h/2h/30m from an earlier checkpoint), skipped if already in the past; cancelling a booking marks its still-pending reminders `CANCELLED` (not deleted, for the audit trail) rather than leaving them to fire for a booking that no longer exists.
- **7 new pytest tests**, all passing against real PostgreSQL. **One real bug caught by the tests themselves**: the first version of the shared `_enqueue` helper built the `NotificationJob` row without actually passing its `dedupe_key` through — a `NOT NULL` column — caught immediately as an `IntegrityError` the first time the tests ran, before it ever reached a commit.
- **New `apps/worker` package**, built from scratch — a notification-job consumer, deliberately **fully self-contained**: it does not import anything from `apps/api` (both packages have a top-level `app` module, which would collide; more importantly a worker process shouldn't share a live ORM mapping with the API process across a boundary like that). Declares its own hand-written SQLAlchemy **Core** `Table` objects (`app/tables.py`) as an explicitly-documented, hand-kept mirror of the relevant parts of `apps/api`'s real schema. Claims jobs with `SELECT ... FOR UPDATE SKIP LOCKED`, holds the row lock for the duration of the Telegram send (a documented simplicity/safety trade-off over introducing an undocumented intermediate "processing" status — a crash mid-send just leaves the job `PENDING` for the next poll), retries with exponential backoff to a terminal `FAILED` status at `max_attempts`, and schedules `BUSINESS_DAILY_SUMMARY` jobs with **no persistent scheduler state** — each poll computes "the next business-local `daily_summary_local_hour`:00" via `zoneinfo` and relies purely on `dedupe_key` existence to avoid duplicates and roll over to the next day. Talks to Telegram via a direct `httpx` POST to the raw Bot API, not `aiogram` (which `apps/bot` uses for launching the Mini App, a different job). Per CLAUDE.md: no in-memory scheduler anywhere in this package.
- **25 new pytest tests** for the worker, run against a dedicated real PostgreSQL database (`bookflow_worker_test`, created via `createdb`) — not SQLite/mocks, because `SELECT ... FOR UPDATE SKIP LOCKED` only exists in real Postgres: message rendering per job type, claim/skip-locked/backoff/terminal-failure behavior, daily-summary date-bucketing and dedupe across multiple poll cycles, and a full integration pass against a mocked Telegram HTTP client (never the real API). **Plus a genuine cross-service smoke test** (scratchpad, not committed): created a real business/owner/customer/Telegram-identity/booking through `apps/api`'s actual service layer against the real `bookflow` database, confirming the worker's hand-kept schema mirror actually matches what `apps/api`'s real Alembic-migrated schema produces — not just the worker's own self-created test schema, which would have missed any drift between the two. `apps/worker` added to `docker-compose.yml`'s default `up` (not profile-gated like `bot`, since it never crashes without a token the way the bot does).
- **Booking status history exposed**: `GET /api/v1/admin/businesses/{business_id}/bookings/{booking_id}/history` (the underlying `BookingStatusHistory` rows already existed and were already being written from an earlier checkpoint — this was purely an exposure task) + a "History" button on each Calendar row opening a dialog with an ordered status timeline. 2 new pytest tests, including a staff member correctly forbidden (403) from viewing another staff member's history.
- **Business analytics dashboard**: `GET /api/v1/admin/businesses/{business_id}/dashboard/analytics?days=N` buckets bookings by business-local date (via `zoneinfo`, at the service layer, per CLAUDE.md's rule — not SQL `date_trunc`), sums completed-booking revenue per day, zero-fills empty days, and returns a status-count breakdown. 2 new pytest tests. **Frontend**: `AdminAnalyticsPage.tsx`, new — a 7/30/90-day range selector, two stat cards, a Recharts v3 `ComposedChart` (bar for bookings, line for revenue, dual Y-axes) and a `PieChart` + legend for status breakdown, using the same status-color palette as the existing `StatusBadge` component.
- **Full backend suite: 79/79 passing** against real PostgreSQL (68 existing + 7 notification + 2 history + 2 analytics). `ruff check` clean on new/modified files bar the same pre-existing `B008`/`C408` stylistic noise already documented in the Phase 3 checkpoint (the worker's own new test files deliberately match that same style for consistency, not by accident).
- **Verification**: `tsc -b` (strict) and `vite build` both clean (the bundle grew from ~515KB to ~912KB with Recharts added — flagged in NEXT_STEPS.md as a code-splitting candidate). `oxlint` clean except the same two pre-existing harmless categories already documented since Phase 2. Then driven end-to-end with a real headless browser (Playwright/Chromium) against the actual local API + Postgres: admin sign-in → Calendar → created a manual booking → opened its History dialog (1 entry) → changed its status → reopened History (2 entries) → navigated to the new Analytics page, confirmed both charts rendered → switched the date-range selector, confirmed no crash. Zero application console/page errors — the only console noise was the same two sandbox-blocked requests (Google Fonts, `telegram.org`) already documented in every prior checkpoint. One script-level bug found and fixed along the way (an ambiguous Playwright `text=` locator that also matched an unrelated `<select><option>` — a test-script bug, not an application bug, scoped away by anchoring assertions to `[role='dialog']` and counting `<ol><li>` entries instead).
- **Demo data reseeded to a clean state** afterward — duplicate test bookings left by the locator-bug-affected first E2E run, plus the final run's own test booking, both cleaned up via direct `psql` deletes; the live ATELIER business is back to its original seed.

## 2026-11-01 — Backend: models, migration, availability engine, booking service, auth, routers, tests

- **Models**: 16 SQLAlchemy 2.x async models covering every entity from the spec plus `AuditLog` (`apps/api/app/models/`).
- **Migration**: `0001_initial_schema` — autogenerated from the ORM, plus a hand-written generated `tstzrange` column and a `btree_gist` EXCLUDE constraint on `bookings(staff_id, during)` scoped to active statuses. Applied against a real local PostgreSQL 16 instance; the overlap rejection was verified directly with `psql`, independent of any application code.
- **Availability engine** (`app/services/availability.py`): computes real slots from business+staff hours (intersected), recurring breaks, one-off exceptions (leave/holiday/closure), existing bookings expanded by a configurable buffer, service duration, slot interval, lead time, and advance-booking window — all in the business's IANA timezone via `zoneinfo`. Found and fixed a real DST edge case during testing: a spring-forward transition could offer the same real UTC instant as two different nominal local slot times; added deduplication by `(staff_id, starts_at_utc)`.
- **Booking service** (`app/services/booking.py`): create/cancel/reschedule/status-transition. Booking creation takes a Postgres advisory transaction lock keyed on the staff member, re-checks for overlaps with `SELECT ... FOR UPDATE`, and still relies on the DB constraint as the final guarantee — verified with a real `asyncio.gather` concurrency test hitting the same slot from two independent DB sessions (exactly one wins). Idempotency keys supported. Cancellation/reschedule respect configurable policy windows, with a staff-override path.
- **Telegram auth** (`app/core/telegram_auth.py`): implements Telegram's documented `initData` HMAC-SHA256 verification exactly (signature + freshness); `initDataUnsafe` is never used for identity. Unit-tested against valid, tampered, wrong-bot-token, stale, and missing-hash cases.
- **Demo mode** (`app/routers/auth.py`): `/api/v1/auth/demo` issues a demo-scoped JWT against the seeded ATELIER business, fully isolated from Telegram identities.
- **Authorization** (`app/core/authz.py`): JWT-backed `get_current_user`, business-role-scoped dependency factory; nothing trusts client-supplied business/staff/price/status.
- **Routers**: auth, businesses (profile/services/staff), availability, bookings (create/mine/cancel/reschedule). Verified end-to-end over real HTTP against the seeded demo business: demo auth → profile → services → real availability (correct Europe/Istanbul↔UTC conversion) → create booking (201) → a second concurrent booking attempt for the same slot correctly rejected (409) → "my bookings" → cancel (200). Two real bugs (lazy-loaded SQLAlchemy relationships accessed outside an async-safe context) were found and fixed during this manual pass.
- **Seed script** (`app/seed.py`): ATELIER — Modern Grooming Studio, 3 staff (with differing weekly schedules and a lunch break), 6 services, staff-service capability mapping, one business-wide holiday exception, 2 historical demo bookings (completed, cancelled).
- **Tests**: 27 pytest tests, all passing against a real `bookflow_test` PostgreSQL database (deliberately not SQLite — the thing under test only exists in Postgres): Telegram auth validity/rejection (6), availability engine incl. a real DST transition (5), overlap prevention at the DB and service layers incl. idempotency (4), a genuine concurrency race (1), status transitions and policy windows (8), multi-tenant isolation (3).
- **Infra**: `pyproject.toml`, `.env`/`.env.example`, local PostgreSQL 16 set up natively in this sandbox (no Docker daemon available here) with `bookflow` and `bookflow_test` databases and the `btree_gist` extension.
