All notable changes to BookFlow. Newest entries at the top. Entries are only added once the described work is actually done and verified, not planned.

## 2026-11-01 — Phase 3 admin frontend: dashboard, calendar, services, staff, settings

- **Routing split** (`apps/web/src/App.tsx`, `main.tsx`): the app now mounts `AdminApp` at `/admin/*` and `CustomerApp` everywhere else, each with its own independent auth provider/context and localStorage token key (`lib/auth.tsx`/`lib/admin-auth.tsx`), so a browser can hold a customer demo session and an admin demo session side by side without either overwriting the other.
- **Admin auth** (`lib/admin-auth.tsx`, `components/layout/AdminAuthGate.tsx`): resolves a demo-admin session (`POST /auth/demo-admin`, reused from localStorage after first sign-in) then `GET /auth/me` to find which business/role to administer — never trusts anything client-stored for that. A stale/invalid token drops itself and shows a retry UI instead of looping.
- **Typed API layer** (`lib/admin-api-client.ts`, `admin-api-types.ts`, `admin-queries.ts`): a fetch client + hand-written TS mirrors of every `app/schemas/admin.py` shape, and a TanStack Query hook per endpoint with correct cache invalidation (a manual booking or status change also invalidates the dashboard query, since both affect its counts).
- **Five pages**, all wired to the real backend built in the previous checkpoint, with loading states, inline error messages, and no silent failures:
  - `AdminDashboardPage` — stat cards (today/upcoming/completed/cancelled), revenue, popular services, staff workload.
  - `AdminServicesPage` — active/archived grouping, a create/edit dialog, archive/unarchive actions.
  - `AdminStaffPage` — staff list with service-tag badges, a create/edit dialog with a toggle-chip service picker, a schedule dialog, and a leave/closure exceptions section.
  - `AdminCalendarPage` — date-range + staff/service/status filters, a manual-booking dialog, and inline status-change buttons scoped to each booking's actually-valid next statuses (mirroring the backend's `VALID_TRANSITIONS`).
  - `AdminSettingsPage` — business profile form, operating hours, booking policy form.
  - `components/admin/ScheduleEditor.tsx` — one reusable weekly-schedule editor (per-day toggle, start/end time, any number of recurring breaks), shared between a staff member's schedule and the business's own operating hours, matching how the backend models both.
- **New UI primitives**: `components/ui/input.tsx`, `label.tsx`, `select.tsx` (a styled native `<select>` — no Radix Select needed for this dashboard's handful of pickers), same hand-written shadcn pattern as the rest of the project.
- **Two real bugs found and fixed before/during verification**:
  1. `main.tsx` had a broken half-finished edit: a JSX reference to `AuthProvider` whose import had already been removed (the provider had correctly moved into the new `CustomerApp`, but the stale top-level usage wasn't cleaned up) — `tsc -b` would have failed outright. Removed the stale wrapper.
  2. `admin-api-types.ts` imported `BookingStatus` from the customer-facing `api-types.ts` for its own internal use but never re-exported it, so `AdminCalendarPage.tsx` couldn't import it — added to the file's existing re-export line.
- **Verification**: `tsc -b` (strict) and `vite build` both clean after the two fixes above (one non-blocking advisory: the main JS chunk is ~515KB, past Vite's 500KB warning threshold — noted as a future code-splitting candidate). `oxlint` clean except the same two categories of pre-existing, already-documented harmless notices from the Phase 2 checkpoint. Then driven end-to-end with a real headless browser (Playwright/Chromium) against the actual local API + Postgres: demo-admin sign-in → dashboard renders → create/edit/archive/unarchive a service → create a staff member with that service assigned → set their weekly schedule → add a leave exception → create a manual booking on the calendar → change its status → edit business profile + booking policy in Settings → revisit the dashboard. Zero application console/page errors — the only console noise was the same two sandbox-blocked requests (Google Fonts, the Telegram WebApp script) already documented for the customer flow, confirmed this time by capturing the actual failed-request URLs rather than assuming the pattern still held.
- **Demo data reseeded to a clean state** after the E2E run (which had created real "E2E Test Facial (Edited)"/"E2E Test Stylist"/"E2E Walk-in Customer" rows and changed the business address/policy) — confirmed via live HTTP that the reseed restored exactly the original 6 services / 3 staff.

### Known deviations / honestly-flagged gaps

- Same booking-service docstring/behavior gap flagged in the backend checkpoint below still applies — not touched this session.

## 2026-11-01 — Phase 3 admin backend: services, staff, business settings, calendar, dashboard

- **Schemas** (`apps/api/app/schemas/admin.py`, new): every admin-facing request/response shape — business profile update (with an IANA-timezone validator), `MeOut`/`MembershipOut`, service/staff create-update-out, weekly-schedule + break + exception shapes, booking-policy out/update, manual-booking-create, booking-status-update, admin booking/customer out (nested service/staff/customer), dashboard summary + service/staff count-out.
- **Auth extensions** (`apps/api/app/routers/auth.py`): `POST /auth/demo-admin` (browser demo mode for the admin dashboard — spec section 19's "a sample admin dashboard, explorable without a real Telegram account," now true for the business-owner side too, not just the customer side) and `GET /auth/me` (current user + every business membership and role, the admin frontend's first call after sign-in).
- **Five new routers**, all under `/api/v1/admin/businesses/{business_id}/...`, all role-gated via the existing `RequireBusinessRole` dependency and never trusting the client for role/business scope:
  - `admin_services.py` — list (incl. archived)/create/update/archive/unarchive. Archiving flips `is_active`; services are never hard-deleted, since historical bookings keep their own price/duration snapshot regardless.
  - `admin_staff.py` — list/create/update, service-assignment (full replace), weekly working-schedule get/replace, schedule-exception (leave/holiday/closure) list/create/delete. The schedule-replace helpers (`load_schedule_out`/`replace_schedule`) are written once here and reused by `admin_business.py` for business-wide hours (`staff_id=None`).
  - `admin_business.py` — business profile get/patch (patch is owner-only), operating hours get/put, booking policy get/patch (auto-creates a default policy row on first read).
  - `admin_bookings.py` — appointment calendar (date-range + staff/service/status filters, 92-day cap), manual/walk-in booking creation (creates a lightweight guest `User`, reuses the exact same concurrency-safe `booking_service.create_booking` the customer flow uses — no parallel booking-creation logic), booking status changes (cancellation routed through the existing `cancel_booking` with a staff-override flag). Staff-role users are server-side restricted to their own bookings — resolved from `Staff.user_id`, never trusted from a query param.
  - `admin_dashboard.py` — today/upcoming/completed/cancelled counts, a completed-bookings revenue estimate, top-5 popular services, top-10 staff workload, all computed with SQL aggregates (`func.count`/`func.sum`/`group_by`), not pulled into Python.
  - Every mutating endpoint across all five routers writes an `AuditLog` row.
- **Testing infrastructure added** (`apps/api/tests/conftest.py`, `tests/factories.py`): a new `client` fixture wraps the real `app.main.app` in an `httpx.AsyncClient`/`ASGITransport`, overriding `get_db` to share the test's own session (so factory-created rows are visible with no cross-connection games) — needed because role enforcement, 403/404/409 status codes, and response shapes can only be verified by actually going through the FastAPI dependency graph, not by calling service functions directly (the existing test style). `make_membership()` factory and `auth_header()` (builds a real signed JWT via the actual `create_access_token`, so tests exercise the real decode path) added alongside.
- **41 new pytest tests** across `test_admin_auth.py`, `test_admin_services.py`, `test_admin_staff.py`, `test_admin_business.py`, `test_admin_bookings.py`, `test_admin_dashboard.py` — role enforcement (owner/manager/staff/non-member/unauthenticated) on every router, business isolation, full CRUD + archive/unarchive, schedule + exception round-trips, manual booking through the real concurrency-safe path (incl. a genuine 409 on overlap), status transitions incl. the cancel-via-status override, staff-can-only-touch-their-own-bookings proven with two staff members and two bookings (not just documented), and dashboard aggregate math checked against a hand-built mix of booking statuses. Full suite: **68/68 passing** (27 existing + 41 new), against real PostgreSQL, same as every prior checkpoint.
- **Real bug found and fixed**: `admin_staff.py::set_staff_services` returned a stale, pre-change `service_ids` list in its own response immediately after a successful update, because the `Staff.staff_services` collection was already loaded into the session's identity map from an earlier lookup in the same request, and SQLAlchemy's `selectinload` doesn't re-fetch an already-loaded collection on a second query by default. A pytest test caught it directly. Fixed with an explicit `db.refresh(staff, attribute_names=["staff_services"])` after the commit. The database itself was always correct — only that one HTTP response was stale — but it's exactly the kind of bug that makes an admin UI feel broken even when the backend logic underneath is sound.
- **Manual verification before the automated tests existed**: a full curl pass against the live seeded ATELIER business — demo-admin sign-in, `/auth/me`, service CRUD + archive (confirmed archived services vanish from the *public* endpoint while staying visible to admins), staff CRUD + schedule + service assignment (confirmed a newly-created, newly-scheduled staff member correctly appears in the public booking flow), manual walk-in booking, status change, and dashboard numbers checked by hand against the seed data.
- **Demo data reseeded to a clean state** after that manual pass (it had left test artifacts — an archived "Test Pedicure", a "Test Barber" staff member, a completed "Walk-in Joe" booking — in the live ATELIER business); confirmed via live HTTP that the reseed restored exactly the original 6 services / 3 staff.
- `ruff check` run; clean on everything new/modified except the same pre-existing, codebase-wide `B008` (FastAPI's idiomatic `Depends()`/`Query()` in argument defaults — present in every router since before this session, including ones already shipped and verified) and `C408` (`dict(...)`-literal style already in `tests/factories.py`) noise — neither introduced by this session, and not something "fix the new files" should mean rewriting project-wide.

## 2026-11-01 — Frontend (full booking flow + My Appointments) and Telegram bot skeleton

- **Frontend stack**: Vite + React 19 + TypeScript 7 + Tailwind CSS v4 (`@tailwindcss/vite`, CSS-first `@theme`). Design tokens in `apps/web/src/index.css` match the spec's palette (warm ivory/beige/charcoal, muted sage/emerald accent) and typography (Manrope display, Inter body).

Functionally/stylistically equivalent to what the CLI would have generated.
- **Telegram integration** (`src/lib/telegram.ts`, `src/lib/auth.tsx`): typed wrapper over `window.Telegram.WebApp`; real `initData` is used when present and non-empty, otherwise the app calls `/api/v1/auth/demo` automatically and shows a "Demo mode" banner — no manual toggle needed.
- **API layer**: typed fetch client + hand-written TS mirrors of every backend Pydantic schema (`src/lib/api-client.ts`, `src/lib/api-types.ts`), and TanStack Query hooks (`src/lib/queries.ts`) for all of it.
- **Booking flow**: `HomePage` (profile + services by category) → `SpecialistPage` (named staff or "any available") → `DateTimePage` (real day-chip + time-grid picker against the live availability endpoint, correct business-timezone display) → `ConfirmPage` (summary, optional notes, idempotency-keyed submit, friendly 409-conflict message) → `SuccessPage`.
- **My Appointments** (`AppointmentsPage` + `BookingCard`): upcoming/completed/cancelled tabs; cancel via a confirm dialog; reschedule via an in-place dialog that re-queries availability for the same service/staff and submits the new time.
- **Verification**: `tsc -b` and `vite build` clean; `oxlint` clean (bar a few intentional, harmless notices — see PROGRESS.md). Then driven end-to-end with a real headless browser (Playwright/Chromium) against the actual local API + Postgres, twice: once through "any available specialist" (book → appears in My Appointments → cancel), once through a **named** specialist (book → **reschedule** to a new real slot → confirmed). Zero application console/page errors in either run.
- **Real bug found and fixed during that pass**: `apps/api/app/seed.py`'s idempotent reseed (`db.delete(business)`) raised `IntegrityError` on the *second* run, because `Business.bookings`/`working_schedules`/`schedule_exceptions` aren't ORM-cascaded (unlike `staff`/`services`, which are) — SQLAlchemy tried nulling their `NOT NULL` FKs in Python. Fixed by issuing a raw SQL `DELETE` on `Business` instead, which lets Postgres's own `ondelete="CASCADE"` handle it correctly (every relevant FK already has it at the DB level). Verified by reseeding twice in a row and re-running the full `pytest` suite (27/27 still pass).
- **Telegram bot skeleton** (`apps/bot`, aiogram 3.x): `/start /help /book /mybookings /support` handlers, reply keyboard with `WebAppInfo` buttons (Open BookFlow / My Appointments / How It Works / Contact Support), polling entrypoint that fails fast with a clear message if `BOT_TOKEN` is unset. Deliberately thin — no DB access, no duplicated booking logic. Verified: installed real `aiogram`, confirmed all modules import cleanly and all 7 handlers register on the `Router`; confirmed the no-token fail-fast path actually exits non-zero with a clear message. **Not** verified against real Telegram servers — no bot token was available (see `apps/bot/README.md` for BotFather setup once one exists).
- **Docker**: `apps/web/Dockerfile` (multi-stage Vite build → nginx with SPA fallback) and `apps/bot/Dockerfile` added; `docker-compose.yml` updated with a `web` service and an opt-in `bot` profile (`docker compose --profile bot up`, since it fails fast without a real token). ## 2026-11-01 — Backend: models, migration, availability engine, booking service, auth, routers, tests

- **Models**: 16 SQLAlchemy 2.x async models covering every entity from the spec plus `AuditLog` (`apps/api/app/models/`).
- **Migration**: `0001_initial_schema` — autogenerated from the ORM, plus a hand-written generated `tstzrange` column and a `btree_gist` EXCLUDE constraint on `bookings(staff_id, during)` scoped to active statuses. Applied against a real local PostgreSQL 16 instance; the overlap rejection was verified directly with `psql`, independent of any application code.
- **Availability engine** (`app/services/availability.py`): computes real slots from business+staff hours (intersected), recurring breaks, one-off exceptions (leave/holiday/closure), existing bookings expanded by a configurable buffer, service duration, slot interval, lead time, and advance-booking window — all in the business's IANA timezone via `zoneinfo`. Found and fixed a real DST edge case during testing: a spring-forward transition could offer the same real UTC instant as two different nominal local slot times; added deduplication by `(staff_id, starts_at_utc)`.
- **Booking service** (`app/services/booking.py`): create/cancel/reschedule/status-transition. Booking creation takes a Postgres advisory transaction lock keyed on the staff member, re-checks for overlaps with `SELECT ... FOR UPDATE`, and still relies on the DB constraint as the final guarantee — verified with a real `asyncio.gather` concurrency test hitting the same slot from two independent DB sessions (exactly one wins). Idempotency keys supported. Cancellation/reschedule respect configurable policy windows, with a staff-override path.
- **Telegram auth** (`app/core/telegram_auth.py`): implements Telegram's documented `initData` HMAC-SHA256 verification exactly (signature + freshness); `initDataUnsafe` is never used for identity. Unit-tested against valid, tampered, wrong-bot-token, stale, and missing-hash cases.
- **Demo mode** (`app/routers/auth.py`): `/api/v1/auth/demo` issues a demo-scoped JWT against the seeded ATELIER business, fully isolated from Telegram identities.
- **Authorization** (`app/core/authz.py`): JWT-backed `get_current_user`, business-role-scoped dependency factory; nothing trusts client-supplied business/staff/price/status.
- **Routers**: auth, businesses (profile/services/staff), availability, bookings (create/mine/cancel/reschedule). Verified end-to-end over real HTTP against the seeded demo business: demo auth → profile → services → real availability (correct Europe/Istanbul↔UTC conversion) → create booking (201) → a second concurrent booking attempt for the same slot correctly rejected (409) → "my bookings" → cancel (200). Two real bugs (lazy-loaded SQLAlchemy relationships accessed outside an async-safe context) were found and fixed during this manual pass.
- **Seed script** (`app/seed.py`): ATELIER — Modern Grooming Studio, 3 staff (with differing weekly schedules and a lunch break), 6 services, staff-service capability mapping, one business-wide holiday exception, 2 historical demo bookings (completed, cancelled).
- **Tests**: 27 pytest tests, all passing against a real `bookflow_test` PostgreSQL database (deliberately not SQLite — the thing under test only exists in Postgres): Telegram auth validity/rejection (6), availability engine incl. a real DST transition (5), overlap prevention at the DB and service layers incl. idempotency (4), a genuine concurrency race (1), status transitions and policy windows (8), multi-tenant isolation (3).
- **Infra**: `pyproject.toml`, `.env`/`.env.example`, local PostgreSQL 16 set up natively in this sandbox (no Docker daemon available here) with `bookflow` and `bookflow_test` databases and the `btree_gist` extension.

- No real Telegram bot token — the auth code path is implemented and unit-tested against a synthetic signed payload, never against the live Telegram API.
- No frontend yet (next up), no admin dashboard (Phase 3), no live notifications (Phase 4), no deployment target exercised (Phase 5).
